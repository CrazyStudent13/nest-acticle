# 举报模块约定

举报（文章 + 用户）模块的前端契约与现行交互（2026-11 新增）。数据模型为**单表多态工单**：`post_report` 一张表以 `targetType`（post/user）区分目标，评论举报是预留口子（字典与后端枚举同步加值即可）。举报理由与目标类型走**数据字典**（运营可扩值，后端流程能力按 targetType 写死不依赖具体 reasonValue）。

## 接口契约（/api/post/report）

| 路由 | 鉴权 | 说明 |
|---|---|---|
| `POST /` | JWT | 提交举报；`{ targetType, targetId, reasonType, reasonContent? }`，返回 `{ reported: true }` |
| `GET /status/:targetType/:targetId` | JWT | `{ reported }`，是否存在**待处理**举报（按钮置灰态；处理完成后恢复可点） |
| `GET /list` | `post:report:list` | 管理端列表（联举报人/处理人昵称 + 目标摘要批查） |
| `PUT /handle/:id` | `post:report:handle` | 处理：`{ status: '1'\|'2', handleAction?, handleRemark? }` |
| `DELETE /batch/:ids` | `post:report:remove` | 管理端批量物理删除 |

- **待处理去重**：同一人对同一目标**同时至多一条待处理举报**——`uk_reporter_pending(reporter_id, target_type, target_id, pending_flag)` 唯一索引 + `pending_flag` 的 NULL 豁免（待处理=1、处理完置 NULL），待处理中重复提交报错「请耐心等待处理结果」（INSERT IGNORE 兜底并发）；**处理完成（成立/驳回）后可再次举报**，历史多行共存
- **举报必须登录**（匿名举报不开放）；禁止举报自己/自己的文章；24h 内跨目标举报上限 10 条
- **理由/目标类型合法性按字典缓存校验**：dictValue 必须存在于 `post_report_reason` / `post_report_target` 的启用项
- **处理状态机**：`0 待处理 → 1 成立 / 2 驳回`（单列三态）；成立时可选处置动作 `unpublish`（下架文章，仅 post 目标）/ `disableUser`（停用用户，仅 user 目标，系统内置账号拒绝）；动作与结论同事务落库，停用的会话清理在事务提交后执行
- **多人举报自动下架（文章）**：同一文章的**不同用户**待处理举报达到 **100 人**时，提交举报事务内自动下架（条件更新，仅已发布时生效、不重复动作）并定向通知作者「已自动下架，待管理员复核」；举报记录保持待处理由管理员复核（可恢复上架）；复核前作者不能自行恢复发布（待处理举报人数达同阈值即拦截，见文章模块 update 口径）

## 处理反馈：sys_notice 定向通知（不单开 tab）

举报反馈本质是一条**私密通知**，走系统通知通道而非通知中心的互动水位模型：

- `sys_notice.user_id`（定向接收人列）：null=全员公告，非 null=仅该用户可见；`sys_notice_type` 字典新增 `'3' 举报反馈`
- **系统通知逐条已读（2026-11-26）**：post_notify_read 以 `category='n:<noticeId>'` 记每用户已读通知——列表行服务端回传行级 `unread`（未读=标题深色+红点，已读=变淡不加粗）；**严格逐条**：进列表页不标已读，点进详情页才标那一条（/post/notify/read-notices）；未读数 = 可见公告中无已读标记的条数（NOT EXISTS），铃铛 total 与左侧 tab 徽标均计入。互动四分类仍是进栏清零的水位模型，两套口径并存
- **处理举报时同事务写入通知**：处理结果必发举报人（成立/驳回 + 处置动作说明）；下架处置另发**被下架文章作者**（「你的文章《xx》已下架」+ 申诉提示）
- 前台「系统通知」栏承接：列表接口带 `scope=mine` 只回全员公告 + 发给本人的定向通知，行首红色「举报反馈」徽标区分；点击进通知详情页（Markdown 正文）
- 管理端通知公告页可管理全部定向通知；`/list?noticeId=` 直取详情时服务端强制做本人可见性校验，私密通知不能越权读取

## 举报弹窗（Report/ReportDialog.vue）

文章/用户共用一个弹窗组件，`targetType` 决定文案与挂点传参：

- **理由选项走字典**：`useDict('post_report_reason')`（弹窗 `v-if` 挂载即登录态，满足字典登录守卫）；运营在管理端扩理由无需发版
- **补充说明可空**，placeholder 联动所选理由（「抄袭搬运」提示贴出处链接，其余「补充说明（可选）」）
- 未登录点击由挂点先拦（`openLogin()`）；提交成功 `emit('done')`，挂点回写「已举报」置灰态并 toast
- 重复举报/频控的业务报错在弹窗内提示（保留填写现场），请求层错误 toast 不重复弹

## 挂点

- **文章页**：左侧 ActionBar 举报按钮，作者本人不渲染（`canReport`）；已举报置灰（`reported` 由详情页登录后补查，切文章/登录后重查）；弹窗挂详情页（post 口径）
- **空间页**：他人空间资料卡操作区（关注按钮旁）举报按钮，本人空间不渲染；已举报置灰，切空间重查；弹窗挂空间页（user 口径）
- **通知中心**：「系统通知」栏承接举报反馈通知（红色徽标），无独立 tab、无红标

## 相关联动（举报处置的下游）

- **下架文章可见性**：guest/detail 对作者本人与后台角色（`post:article:edit`）开放已下架文章，详情页顶部出「已下架」横幅；guest/list 在**空间主人看自己**时一并返回已下架行（带红字「已下架」小标，草稿仍只在创作者中心）；其他访客维持「仅已发布/文章不存在」，不泄露下架存在性
- **作者自管理**：创作者中心的上下架走 `PUT /post/article`（此前服务端剥离状态字段，2026-11-25 修通）——作者只能切换自己文章的已发布↔已下架，**因举报被下架的文章不能自行恢复发布**（存在成立的举报下架记录即拦截，申诉走管理员）
- **停用用户对外可见**：`GET /system/user/guest/profile` 返回 `status`（0 正常 / 1 停用），他人空间资料卡在停用时展示「该用户已被停用」灰标，其文章仍可浏览（停用只封登录，不连带下架内容）；管理端用户状态列走字典 `sys_normal_disable`（正常/停用）
